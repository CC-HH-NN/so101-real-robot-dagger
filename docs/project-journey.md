# 项目历程：把模型接成一条真机闭环

这个项目的主线不是“训练一个抓放模型”，而是把一个视觉策略从数据、训练和推理，接到真实 SO-101 机械臂上，并让每次失败都能回到可分析、可改进的工程流程中。抓放任务只是一个足够具体、容易重复的验证载体。

## 1. 先让真机状态可观察

项目从双摄画面、关节反馈和串口状态开始。每次运行同时记录观测、模型目标、实际下发命令、机械臂反馈和人工评分。这样可以回答“模型没有输出”“命令没有送到”“机械臂没有跟上”以及“任务本身失败”之间的区别。

这一步也暴露了真实系统的边界：相机帧可能过期，远程推理存在往返时间，动作块需要在下一块到达前接续，串口可能出现超时或舵机状态错误。没有这些记录，所有问题都会看起来像模型失败。

## 2. 用同一条执行链比较不同策略

ACT、远程 Diffusion Policy、π0、π0.5 和 π0.5 Training-Time RTC 都接入同一台机械臂、同一类任务和同一套人工评分标准。固定点位结果为 47/50，作为工程基线；这个结果用于比较部署链路下的实际表现，不代表任意场景泛化。

统一入口的价值在于把模型差异和系统差异拆开：相机配置、动作单位、执行反馈、回位流程和评分口径保持一致，模型才有可比较的条件。

## 3. 从日志拆解端到端延迟

延迟不是一个数字。项目分别关注相机帧年龄、双摄对齐、网络往返、服务端推理、动作块长度、RTC 接续余量、队列是否耗尽、串口发送和机械臂反馈。

例如，RTC 运行中出现过“动作接续不足”和“相机帧失效”两类停止。它们的处理方式不同：前者要看动作块和接续预算，后者要看观测时效和网络/服务负载。把两者分开，才能知道该改模型、改调度，还是改现场链路。

## 4. 把失败变成 DAgger 数据

模型在真实场景中出现偏移或抓取失败后，操作者暂停模型、接管主臂并完成剩余任务。每条 DAgger episode 保留从起点开始的完整轨迹，同时逐帧标记 `intervention=False/True`，用于区分自主阶段与人工阶段。

完整轨迹用于追溯和展示；训练窗口从连续、有效的人工纠正段提取，跨越暂停的部分不拼接未来动作。这样既保留失败发生前的上下文，也避免把时间上不连续的动作当成一段监督信号。

## 5. 训练与筛选围绕真实问题进行

训练时保留原始示范的时间尺度和归一化统计，把原始示范与人工纠正放在同一训练框架下比较。短片段、硬件中止、复位失败和时间轴断裂都单独标记，不因为“有文件”就直接进入训练。

多个 checkpoint 通过相同的远程 RTC 部署链复测。重点不是单看训练 loss，而是观察模型是否真的改善了起点动作、抓取过程和小范围位置变化；如果性能下降，还要回到数据比例、时间窗口和动作执行日志继续定位。

## 6. 用少量典型条件做泛化复测

在固定点位基线上，项目用 π0.5 Training-Time RTC + DAgger 选择了两类容易解释的位置变化：玩偶前移 3 cm、玩偶侧移 6 cm。DAgger 后，前移条件从 20% 提升到 70%，侧移条件从 30% 提升到 90%。ACT 和远程 DP 没有在公开协议中报告位置泛化数字；这些结果也不等于任意位置或任意物体泛化。

## 7. 最终沉淀的工程经验

- 真机闭环的第一步是把观测、目标、实发、实测和结果分开记录。
- 模型成功率必须和技术中止、相机时效、网络往返、队列耗尽及硬件故障分开统计。
- DAgger 不只是“再采几条数据”，而是把真实失败状态和人工恢复动作重新送回训练流程。
- 完整轨迹、训练窗口和展示视频承担不同职责，不能互相替代。
- 真机比较应固定执行链和评分协议，再讨论模型差异。
- 泛化结论必须绑定具体变化、回合数和成功判据，不能从少量条件外推到任意场景。

公开副本用结果表、协议、架构说明和精选视频展示这条闭环；权重、训练数据、标定和内部部署环境继续保留在私有工作区。
