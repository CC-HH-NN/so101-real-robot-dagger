# 项目历程：把模型接成一条真机闭环

抓取—放置为项目提供了一个可重复的验证任务，工程主线沿着“观测真机 → 采集数据 → 统一部署 → 诊断失败 → 人工纠正 → 再训练 → 泛化复测”展开。每个阶段都保留输入、输出和验证边界，方便回到具体证据复盘。

## 1. 先让真机状态可观察

最初的重点是把双摄画面、关节反馈、串口状态和动作时间戳同时写入运行记录。单独看视频只能看到结果，加入模型目标、实际下发和实测状态后，才能区分模型没有输出、命令没有送到、机械臂没有跟上和任务本身失败。

观测链路还暴露出相机帧年龄、双摄对齐、远程推理往返、动作块接续和串口反馈等约束。后续诊断围绕这些可测量量展开，避免用“模型失败”概括所有停止原因。

## 2. 用同一条执行链比较策略

ACT、Diffusion Policy、π0、π0.5 和 π0.5 Training-Time RTC 接入同一类 SO-101 任务、相机输入、回位流程和人工评分。固定点位结果为 47/50，形成部署链路下的工程基线。

统一入口把模型差异与系统差异拆开：相机配置、动作单位、反馈、回位和评分口径保持一致，结果才具备可比性。Diffusion Policy 采用远程推理，表中使用全称以避免与其他 DP 实现混淆。

## 3. 把延迟拆成可定位的组成部分

延迟按相机帧年龄、网络往返、服务端推理、动作块长度、RTC 接续余量、队列状态、串口发送和机械反馈分别记录。RTC 的“接续不足”和相机的“帧过期”由不同环节触发，处理方式也不同：前者关注动作块与训练期接续预算，后者关注观测链路与调度长尾。

动作队列耗尽时，系统会区分请求在途、服务故障、相机失效和真实超时；在明确边界内等待新块，超过时限则保留技术中止证据。这样既保护机械臂，也避免把链路故障混入模型成功率。

## 4. 把失败变成 DAgger 数据

模型出现位置偏移后，操作者暂停模型、接管主臂并完成剩余任务。每条 episode 从起点开始保存，逐帧标记 `intervention=False/True`。完整轨迹用于回放、展示和失败归因，连续人工纠正窗口用于训练。

暂停造成的时间断点不拼接未来动作；硬件中止、复位失败和未来动作不足的尾段分别标记。人工接管路径使用原始主从采集的 Goal_Position 语义，模型执行保护与人工操作语义分开管理。

## 5. 训练筛选围绕真实失败

训练阶段保留原始示范的时间尺度和归一化统计，把人工纠正作为新增分布加入原始示范。起点监督单独检查，因为纠正数据往往从模型已经偏离的位置开始，直接提高纠正数据比例可能稀释起步动作。

多个 checkpoint 通过同一远程 RTC 部署链复测。训练 loss 反映优化过程，真机成功率、首次抬臂时序、抓取过程和位置变化反映行为结果；两类证据分开记录。

## 6. 用典型位置变化做泛化复测

固定点位基线之后，选择玩偶前移 3 cm 和侧移 6 cm 两种变化，篮子、相机和起点保持不变。π0.5 Training-Time RTC + DAgger 的成功率分别从 20% 提升到 70%、从 30% 提升到 90%。这些结果与具体位移和回合数绑定，描述小范围位置变化下的改进幅度。

## 7. 工程经验沉淀

- 先记录观测、目标、实发、实测和评分，再讨论模型优劣。
- 成功率、技术中止、相机时效、网络往返、队列耗尽和硬件故障分别统计。
- 完整轨迹、训练窗口和展示视频承担不同职责，来源与时间轴保持一致。
- 人工接管要沿用真实采集语义，避免模型执行保护误拦纠正动作。
- 位置泛化结论必须绑定具体变化、回合数和成功判据。

故障的逐项现象、根因、处理和证据边界见 [`failure-analysis.md`](failure-analysis.md)。
